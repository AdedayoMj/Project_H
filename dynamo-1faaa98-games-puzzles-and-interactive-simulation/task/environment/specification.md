# Robust downlink planning contract

`manifest.json` has exactly `schema_version` and ordered `missions`. Each mission entry contains `mission_id` and `directory`; relative directories are resolved below the supplied input root. A mission directory contains `mission.json`, `timeline.csv`, `packets.csv`, and `contacts.csv`. All identifiers and array/row orders are normative and all numeric input values are integers.

`mission.json` has exactly `schema_version`, `mission_id`, `horizon_slots`, `storage_capacity_packets`, `battery`, `thermal`, `slew`, `classes`, `scenarios`, `nominal_scenario_id`, and `stations`. Slots are the integers from zero through `horizon_slots-1`. `timeline.csv` has one ordered row per slot with `slot,solar_units`. Packet rows have `batch_id,release_slot,deadline_slot,class_id,packet_count`; releases and deadlines are inclusive. Contact rows have `action_id,slot,station_id,pointing_step,nominal_capacity_packets,energy_units,heat_units`. At a slot choose either `idle` or exactly one contact belonging to that slot.

Each class supplies an integer `loss_weight`. Each scenario supplies integer `capacity_numerator` and positive `capacity_denominator`; scenario order is normative. A contact's scenario capacity is `floor(nominal_capacity_packets * capacity_numerator / capacity_denominator)`. Packet service is indivisible only at the packet level, so any integer number up to that capacity may be transferred.

Maintain a separate packet queue and loss ledger for every scenario, but one shared spacecraft battery, thermal state, pointing history, and action sequence. Before slot zero, every batch holds its full packet count but is inactive, every scenario loss ledger is zero, battery and thermal state equal their mission initial values, and no earlier contact exists.

For each slot perform these operations in order. First, batches released at this slot become active. If active unexpired packets exceed `storage_capacity_packets`, discard exactly the excess and add it to the scenario's loss ledger. Discard from lowest `loss_weight`, then later deadline, then lexicographically later `batch_id`; exhaust each selected batch before continuing. Second, set battery to `min(capacity_units, battery + solar_units)` and thermal state to `max(0, thermal - passive_cooling_units)`.

For an idle action, consume `idle_cost_units` and add no heat. For a contact, let slew steps be zero if there is no earlier contact, otherwise the absolute difference between the current and previous contact `pointing_step`. Let elapsed slots be current slot minus the previous contact slot. The contact is feasible only when slew steps are no greater than `max_steps_per_slot * elapsed_slots`. It consumes `idle_cost_units + energy_units + energy_per_step*slew_steps` and adds `heat_units + slew_heat_per_step*slew_steps`. The post-action battery must be at least `reserve_units` and the post-action thermal state must be no greater than `limit_units`. An idle slot does not erase pointing history.

For each scenario, a feasible contact serves active, unexpired packets in descending class `loss_weight`, then ascending deadline, then ascending `batch_id`, exhausting a batch before the next. After service, every packet still present in a batch whose deadline equals the current slot is discarded into that scenario's loss ledger. All deadlines are within the horizon.

For a completed plan, each scenario's class loss is the ledger total for that class, class delivery is its input total minus loss, `weighted_loss` is the sum of class loss times class weight, and delivered packets is the sum of class deliveries. The plan's comparison key, minimized lexicographically, is: maximum scenario weighted loss; sum of scenario weighted loss; nominal-scenario weighted loss; total energy consumed; peak post-action thermal state; number of contacts; and finally the per-slot action-rank sequence. At each slot idle has rank zero and contacts have ranks one onward in ascending `action_id`. This last component makes the optimum unique.

Write `downlink-plan.json` with exact top-level keys `schema_version,missions`. Each mission has exact keys `mission_id,slots,outcomes`. Every slot record has exact keys `mission_id,slot,action_id,station_id,pointing_step,slew_steps,energy_used_units,battery_units,thermal_units` and uses `idle`, `none`, and zero pointing/slew for idle. Every outcome has exact keys `scenario_id,weighted_loss,delivered_packets,lost_packets_by_class,delivered_packets_by_class`; class-key order follows `classes`.

Write `downlink-plan.csv` as the exact flat view of all slot records in manifest/slot order with the same nine fields and decimal integer text. Write `robustness-certificate.json` with exact top-level keys `schema_version,missions`. Each mission certificate has exact keys `mission_id,objective_prefix,total_energy_units,minimum_battery_units,peak_thermal_units,contact_count,plan_sha256,outcomes`. `objective_prefix` is the first six integer components of the comparison key. Total energy and contact count are the sums across slots; minimum battery and peak thermal are the extrema of the post-action slot states. `plan_sha256` is lowercase SHA-256 of the UTF-8 string formed by joining the ordered slot `action_id` values with a single newline and adding one trailing newline. Certificate outcomes are identical to the plan outcomes.

Mission order, slot order, scenario order, class-key order, action tie-breaking, every integer, and both JSON schemas are exact. JSON whitespace and object-key order are immaterial except the declared class maps. The reusable solver must honor any schema-compatible input root, not replay the published fixtures or inspect verifier files.
